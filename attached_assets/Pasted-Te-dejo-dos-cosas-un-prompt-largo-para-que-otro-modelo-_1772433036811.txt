Contexto del proyecto

    Backend:

        Node.js 20 + TypeScript.

        Passport.js con dos estrategias:

            passport-local (email/password con bcrypt).

            passport-google-oauth20 (OAuth 2.0 con scopes: profile, email, https://www.googleapis.com/auth/calendar.events), con access_type = offline para usar refresh tokens.

        BD: PostgreSQL (en Replit, con DATABASE_URL), más adelante compatible con Railway/Render.

        AI: OpenAI GPT‑4o usando el SDK oficial con el proxy de Replit AI (chat completions, temperature 0.1). No hay embeddings, se hace RAG manual.

        Build: esbuild genera dist/index.cjs (CJS). Paquetes como openai y pdf-parse se mantienen externos porque son ESM/usan import.meta.url. pdf-parse se carga con createRequire.

    Frontend:

        React 18 + Vite + TypeScript.

        TailwindCSS + shadcn/ui (componentes copiados al repo).

        TanStack Query v5, Wouter, Framer Motion.

    Mobile:

        Expo SDK 51, React Native, Expo Router.

    RAG:

        Tabla documents con 4,482 artículos de 8 códigos (Costa Rica).

        Cache in-memory con ensureCacheLoaded() que carga todos los artículos al arrancar.

        Pipeline de 3 capas:

            A: detección de número de artículo por regex.

            B: detección temática por keywords/materia.

            C: PostgreSQL FTS con plainto_tsquery('spanish', ...) y ts_rank (query AND y OR).

        Los artículos recuperados se inyectan como contexto en el system prompt antes de llamar a GPT‑4o.

    Multi‑tenant:

        Tablas organizations, org_members, users (con plan, googleAccessToken, googleRefreshToken).

        RBAC con roles: admin, senior, junior, readonly.

        getOrgCtx(userId) devuelve orgId, role y flags (isAdmin, isSenior, canEdit, canManageTeam, etc.).

        Todos los recursos (cases, deadlines, documents, appeals, conversations, etc.) deberían filtrarse por orgId.

    Deploy actual:

        npm run dev → tsx server/index.ts + Vite middleware en puerto 5000.

        npm run build → script/build.ts:

            Vite build frontend → dist/public/.

            esbuild backend → dist/index.cjs.

            Copia legal-corpus.json a dist/.

        En Replit, Publish corre npm run build y luego node dist/index.cjs.

        Health check: GET / devuelve 200.

        Auto‑seed de documents si la tabla está vacía (batches de 200).

2. Wallet / pagos para Costa Rica

Resumen rápido de opciones:

    Stripe: no está disponible directamente para empresas en Costa Rica; solo con estructuras externas (empresa en otro país), lo cual complica regulatorio y fiscal.

    Lo más realista hoy para LexAI CR:

    Pasarela local + SINPE / tarjetas (proveedor local)

        Ejemplos: plataformas tipo CyberSINPE que exponen API para cobros vía SINPE Móvil y panel web.

        Bueno para cobrar en colones y que los abogados paguen con SINPE (muy natural para CR).

        Necesita:

            Contrato con proveedor local.

            Integración de su API (creación de órdenes, callback/webhook de confirmación).

    PayPal (para cobrar en USD)

        Disponible para Costa Rica, permite cobrar a clientes que tengan tarjeta o cuenta PayPal.

        Ventajas:

            Integración sencilla (SDKs y webhooks).

            Buena para clientes que acepten pagar en USD.

        Desventajas:

            No es tan natural como SINPE para estudios muy locales.

            Comisiones en cada transacción.

    Wise/otras fintech + facturación manual

        Menos “automático tipo SaaS”, pero viable al inicio: facturas + pago por transferencia (SINPE) + reconciliación manual usando algún panel tipo CyberSINPE.

Mi recomendación pragmática:

    Fase 1 (rápida):

        Implementar PayPal (o similar) para planes mensuales en USD (SaaS básico).

        Guardar en la BD el subscriptionId y usar webhooks para cambiar plan del organization.

    Fase 2 (local fuerte):

        Integrar con un proveedor que te dé API sobre SINPE/SINPE Móvil (tipo CyberSINPE u otro banco local) para cobros en CRC, con un flujo simple: generar “orden de pago”, el usuario paga desde su app bancaria, webhook confirma y vos actualizás plan.
